- S0 and S2: carry the agent's tool names on the run. Proposal: `startRun` takes `tool_names` (list of string, default empty), `Run` returns it, and the SDK's `wrap` fills it from the `tools=` it sees (the demo agent passes its 11 tool names). The `RunReader` adapter maps it to `RunView.tool_names`. Without it, fixes that need a tool the run never called (block instead of callback) usually fail.

- How S0 wires the engine:
  - At startup, one `llm = fd_engine.llm.Llm(EngineSettings())` per process (raises `LlmNotConfiguredError` without `OPENAI_API_KEY`).
  - Per diagnosis: `Diagnoser.with_llm(llm, reader=, runner=, sink=, settings=).diagnose(run_id, diagnosis_id) -> DiagnosisResult`.
  - After it, if `result.explanation` is set: `CauseGrouper(llm).match(result.explanation, candidates)` with the project's causes as `CauseCandidate` (id, title, category, summary). It returns `cause_id` or None for a new cause. Add `match.cost_usd` to the diagnosis cost.
  - Benchmark (S4): `BaselineJudge(llm).predict(run, steps) -> BaselinePrediction(step, reason, cost_usd)`.
- Adapter notes for S0:
  - `Check` has no id. The sink keys a check on (`diagnosis_id`, `index`): `check_started` inserts it as `pending`, `check_finished` updates passes and result.
  - `ReplayRunner.replay` returns exactly `samples` outcomes; a timed-out job is `errored`. The engine also wraps each call in `FD_ENGINE_REPLAY_TIMEOUT_SECONDS`.
  - The engine sets status `bisecting`, `verifying` and `explaining` through `progress`. The API sets `done` or `failed` when it stores the result.
  - `diagnose` raises `ReplayUnavailableError` (code `replay_unavailable`, retryable) when every replay in a check errored, and `CheckBudgetError` (code `check_budget_exceeded`). Store the code as the diagnosis `error_code`.
  - An explanation is produced for every found step, verified or not; `verdict_kind` says which.
  - Fixed turns carry minted tool call ids (`call_fd_...`). The worker must use them as `tool_call_id` on the tool results it records.
